# Screen size compatibility for virtual windows

On an iPad held in landscape, a portrait-shaped virtual game window can have different dimensions from `UIScreen.mainScreen`. Some advertising SDKs and popup layouts use the screen dimensions instead of the presenting window, so their content can be oversized, clipped or laid out for the wrong aspect ratio.

Starting in 3.8.22, **Use Window Size as Screen Size (Experimental)** is available in each app's settings. It defaults off and applies to that app's virtual LiveProcess windows. Close and relaunch every account after enabling or disabling it; changing the setting does not modify an already running process. The toggle is unavailable when the app disables TweakLoader injection. Native iPad windows, ordinary launches and other apps do not opt in. Turning it off and relaunching restores the original screen APIs; no container migration or save-file changes are needed.

For direct calls from an opted-in game or its third-party SDK, the compatibility hook reports the main game's logical content dimensions for `UIScreen.bounds`, `applicationFrame`, `nativeBounds` and screen coordinate-space bounds. The host supplies initial content geometry before guest constructors run. Once the game has a window, its bounds are used directly: they already account for content scale and exclude the host's decorative window bar. An ad becoming key does not replace that game window. Fixed/native dimensions use the local window's orientation and native scale. External screens retain their original APIs.

In 3.8.22, restoring four accounts could leave the third/fourth game's internal aspect ratio different even when all outer frames matched. Workspace restoration launched accounts before applying saved layout and scales, so early game/SDK reads could cache an intermediate one/two/three-window size. Version 3.8.23 reserves the saved accounts' final grid slots during launch, applies saved layout/proportions before starting them, and sets each account's scale and laid-out content bounds before its extension request. Final restoration applies scene geometry immediately without an intermediate grid animation. Missing apps/containers are excluded from the launch plan; failure or cancellation clears any remaining reservations. Saved account sizes may intentionally differ if the workspace has unequal divider proportions or different scales.

Ordinary virtual-window launches also settle their content frame before starting. Pre-scene layout changes do not apply guest scale to the host content view; once the private presenter exists, the new hosting view receives the saved transform before its initial frame update. These changes do not modify existing workspace snapshots, account data or the guest screen hooks. Test the affected saved workspace directly after closing all four accounts; an already-running game may keep dimensions cached from its earlier launch.

The screen coordinate-space objects and their point/rectangle converters stay unchanged. UIKit's own geometry queries retain physical dimensions, selected from the immediate caller's system-library image; unidentified callers also retain original behavior. UIKit relies on those original identities and physical transforms when creating or rotating windows. The dimensions option is intended for screen-based sizing; use the window's coordinate space for actual guest input. It does not create a replacement screen or a custom scene transform.

Main-thread queries refresh geometry. Window frame/bounds changes and existing lifecycle notifications refresh a locked snapshot for background SDK reads; background queries do not enumerate UIKit windows or wait on the main thread. No timer or idle polling is added. The last valid dimensions survive temporary scene disconnection. An established game scene remains selected when a popup creates other windows, while ambiguous initial application scenes retain the startup snapshot.

This is a dimensions compatibility option, not a replacement for UIKit scene geometry. It does not change `UIWindowScene.interfaceOrientation`, `UIDevice.orientation`, the physical display configuration, orientation masks, host rendering or Input Sync's window coordinates. An SDK that infers layout from local screen dimensions may improve; one that reads device/scene orientation, cached dimensions or a system view service can still behave differently. WebKit's JavaScript `screen.*` and orientation belong to its web process and are not rewritten; a responsive web popup should use its viewport. A video designed only for landscape may still require letterboxing or a separate SDK-specific fix.

The UIKit checks exercise the production hooks with a real window, modal close-button hit testing, web viewport layout, retained coordinate conversion, resize, startup and background reads, plus controlled landscape/portrait scene geometry, ad-window replacement and exclusions. They do not load Monster Strike or its advertising SDK. The affected four-account iPad setup still needs the comparison in [the device checklist](../Tests/MultitaskManualChecks.md) before this option can be considered confirmed for that game.
