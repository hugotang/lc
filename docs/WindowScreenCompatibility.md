# Screen size compatibility for virtual windows

On an iPad held in landscape, a portrait-shaped virtual game window can have different dimensions from `UIScreen.mainScreen`. Some advertising SDKs and popup layouts use the screen dimensions instead of the presenting window, so their content can be oversized, clipped or laid out for the wrong aspect ratio.

Starting in 3.8.22, **Use Window Size as Screen Size (Experimental)** is available in each app's settings. It defaults off and applies to that app's virtual LiveProcess windows. Close and relaunch every account after enabling or disabling it; changing the setting does not modify an already running process. The toggle is unavailable when the app disables TweakLoader injection. Native iPad windows, ordinary launches and other apps do not opt in. Turning it off and relaunching restores the original screen APIs; no container migration or save-file changes are needed.

For direct calls from an opted-in game or its third-party SDK, the compatibility hook reports the main game's logical content dimensions for `UIScreen.bounds`, `applicationFrame`, `nativeBounds` and screen coordinate-space bounds. The host supplies initial content geometry before guest constructors run. Once the game has a window, its bounds are used directly: they already account for content scale and exclude the host's decorative window bar. An ad becoming key does not replace that game window. Fixed/native dimensions use the local window's orientation and native scale. External screens retain their original APIs.

In 3.8.22, restoring four accounts could leave the third/fourth game's internal aspect ratio different even when all outer frames matched. Workspace restoration launched accounts before applying saved layout and scales, so early game/SDK reads could cache an intermediate one/two/three-window size. Version 3.8.23 reserves the saved accounts' final grid slots during launch, applies saved layout/proportions before starting them, and sets each account's scale and laid-out content bounds before its extension request. Final restoration applies scene geometry immediately without an intermediate grid animation. Missing apps/containers are excluded from the launch plan; failure or cancellation clears any remaining reservations. Saved account sizes may intentionally differ if the workspace has unequal divider proportions or different scales.

Ordinary virtual-window launches also settle their content frame before starting. Pre-scene layout changes do not apply guest scale to the host content view; once the private presenter exists, the new hosting view receives the saved transform before its initial frame update. These changes do not modify existing workspace snapshots, account data or the guest screen hooks. Test the affected saved workspace directly after closing all four accounts; an already-running game may keep dimensions cached from its earlier launch.

On 2026-10-25 the user reported that the affected four-account saved-workspace proportion retest passed in 3.8.23. This confirms the reported third/fourth-account internal-proportion regression in their setup. The user subsequently confirmed that the ad remained oversized/clipped within its own game window in 3.8.24, despite enabling the option and closing/relaunching all four accounts. The earlier screen hooks were insufficient for that ad.

Version 3.8.24 adds independent top/bottom grid reservations for landscape, remembered separately from portrait and by each saved workspace. Existing snapshots keep the landscape defaults: top reserved and bottom extended. The startup slot plan applies these choices before guest launch, so all accounts receive content dimensions from the final reserved area. This changes grid layout without changing the screen hooks, system side safe areas or physical/scene orientation.

Version 3.8.25 extends the same opt-in in two places. A game/SDK-created secondary `UIWindow` in the bound game's scene that starts with whole-scene or physical-screen dimensions is fitted to the game's frame during initialization, frame/bounds assignment or presentation. Once fitted, it follows game resize/rotation while it retains that fitted frame. A custom smaller popup rectangle relinquishes automatic fitting; the bound game, unmarked system windows and other scenes are excluded. The association is weak and uses existing window changes, without a timer.

For `WKWebView` pages in the opted-in guest process, a document-start compatibility user script reports JavaScript `screen.width`/`height` and `availWidth`/`availHeight` from the top page's visual viewport multiplied by its scale. This gives the unobscured web-view dimensions at initial scale, rather than the physical display or an iframe's smaller area. Automatic scroll insets can make these values differ from the native view's point dimensions. Same-origin frames read the top viewport directly; cross-origin frames start with the game's launch snapshot and receive only dimensions from their parent through `postMessage`. Resize events propagate updated dimensions, without polling. The script runs before retained guest scripts, whose relative order is preserved; content controllers, message handlers, data stores and navigation delegates remain. It changes no web storage, ad network requests or physical orientation.

When the SDK leaves `preferredContentMode` at Recommended, the configuration uses Mobile so iPad's desktop browsing does not ignore a mobile ad's viewport meta tag. An explicit Mobile or Desktop choice is preserved. This covers screen-sized HTML inside a correctly sized web view; an SDK's separately oversized native web-view frame or per-navigation override can still require another fix. An attempted WebKit `ShouldReportViewportSizeAsScreenSize` preference failed the same tests because page policies override it; that ineffective SPI is absent from the resulting implementation.

The added reproductions failed against 3.8.24: a scene-created ad window retained scene dimensions, and a 300 × 500 pt web ad read `screen.width` as 768 instead of 300. These are supported failure paths, not proof of which SDK path Monster Strike uses. On 2026-10-25 the user confirmed that the affected ad display was fixed in 3.8.25. Other ad types, scale combinations and rotation while an ad is open have not been separately confirmed.

The user also identified a separate orientation-history problem in 3.8.25: at the same final landscape four-account layout, restoring in portrait and then rotating produced more correct game proportions than restoring directly in landscape. All four accounts used 100% content scale. The game may cache its startup dimensions, but this report alone does not establish that cause. The host's first scene parameters specified the physical display without explicitly providing the prepared logical content frame, and initial scene configuration preceded the saved hosting transform. It also had an inconsistent activation calculation: it subtracted a scaled bar from the unscaled decorated frame, while normal resize used the actual content view. That separate discrepancy occurs at 50%/200% scale and does not explain the user's 100% report by itself.

Version 3.8.26 uses the laid-out content view for launch metadata, first scene parameters, scene activation and later resize. Modern virtual hosting views receive explicit logical bounds, saved scale and zero origin before initial scene configuration; later changes apply the same operation. Both initial scene parameters and legacy scenes divide by content scale once. Each host orientation still uses its own grid shape, saved divider proportions and reserved areas. No portrait startup reference, fixed game aspect ratio or replacement device/scene orientation is introduced. Rotating continues to send the new dimensions; the existing guest screen and ad hooks then use the current game bounds.

The regression fixtures compare portrait restore → landscape, direct landscape restore and both paths back to portrait, with both landscape layouts, independent reserved areas, unequal saved proportions, multiple scales and shown/hidden top/bottom bars. They also check initial logical bounds, scaled close-button hit testing and background screen updates. They cannot force a game's renderer to discard private cached layout. On 2026-10-26 the user tested 3.8.26 and reported that the game still retained its startup proportions in both rotation directions. The device check failed; neither the actual guest geometry after rotation nor the renderer's behavior is established by these fixtures.

Version 3.8.27 explicitly submits completed modern virtual hosting geometry through UIKit's existing `_updateSceneSettingsFromSettingsProvidersWithFence:` controller method, when available. It uses the hosting view's real bounds/transform and UIKit's own settings providers and fences. Requests coalesce on the main queue; unchanged geometry does not resubmit, reentrant changed geometry gets one more check, and PiP/closed/detached scenes cannot send pending work. This improves the delivery path without assuming the game will discard a cached layout. Each orientation still uses its own live grid; no fixed portrait canvas is imposed. Legacy and native-window paths retain their existing behavior.

On 2026-10-26 the user supplied 3.8.27 diagnostics and confirmed that proportions remained incorrect after landscape launch → portrait rotation. The host content, guest scene, game window, root view and Metal layer all changed from 297 × 834 to 416 × 596 pt. The drawable changed from 594 × 1668 to 832 × 1192 pixels at scale 2, and the published screen dimensions followed. Host request/reply geometry agreed. The explicit hosting method was unsupported on that iPad and its submission count was zero; UIKit's original delivery path resized the guest. An unchanged window/drawable is therefore excluded for this measured path. These dimensions cannot locate any cached game UI/camera/projection calculation. The initial-size field records launch history and is expected to remain 297 × 834.

Version 3.8.28 addresses a separate callback-timing path. UIKit's `viewWillTransitionToSize:withTransitionCoordinator:` can run while the window still has its old dimensions. Only inside an eligible bound game's full-window root callback, direct game/SDK screen reads use the announced destination size, including reads in an app override before it calls super. The original implementation runs once with its original size and coordinator; the wrapper neither sends another transition nor resizes a view/layer. Actual-window reads resume on return, including an exception. Nested child/ad callbacks cannot replace the root's screen size, and background threads continue using actual-window snapshots. Native/fixed dimensions use the destination's local shape; physical/device/scene orientation and UIKit's physical converters stay unchanged. No fixed canvas or portrait launch reference is introduced.

The next diagnostics include root-controller/root-view/render-view class names and the bound root's `sizeTransitionCount`/`lastSizeTransition`: target size, actual window size, published compatibility size and scene orientation at callback entry. Only the latest eligible callback is retained, with no periodic sampling, screenshots or account data. A zero count after rotation identifies an unobserved/ineligible root callback; an increased count does not prove that the game used the compatibility screen size or rebuilt its camera. This callback correction is tested with controlled app overrides, including pre-super reads, inherited overrides, nested children, ad exclusion, background reads, exceptions and disabled hooks. On 2026-10-26 the user reported that Monster Strike's proportions still failed in 3.8.28. No new callback diagnostic accompanied that report, so receipt of the wrapped root callback is not established. The passing controlled tests do not pass the physical-game check.

During 3.8.28 validation, the existing WebKit rotation test observed a 600 × 400 viewport and matching screen API while the test ad still had its old 300-point width. An independent event-order reproduction showed that a window resize delivered before the visual viewport's new dimensions can cause an ad to lay out once using the old screen size. The previous visual-viewport listener only broadcast to child frames. The script now also dispatches a window resize when its published dimensions change after that first event; unchanged viewport notifications only broadcast. The window listener records the dimensions it announced, preventing duplicate relayout or a recursive event loop. Auxiliary-window fitting, mobile-mode selection, iframe sizing and account data remain. The controlled event-order regression tests the production script, not the game's ad SDK.

On 2026-10-26, IDA/Hex-Rays analysis of the user-supplied Monster Strike 33.0.0 iOS executable identified separate startup game/render dimensions and current output dimensions. Startup normalizes the game canvas, chooses cocos design resolution and UI margins, and enables bgfx DynamicScreen compositing. The examined root transition completion and `EAGLView.layoutSubviews` resize the output; the composite frame-start branch retains logical game dimensions while fitting/cropping/centering them into that output. The root transition method contains no direct screen-size query or design recalculation. This explains why the measured window/root/Metal/drawable resize can coexist with startup-dependent proportions; another generic screen callback does not establish a game relayout. No complete, repeatable relayout entry point was identified. Static analysis does not exclude all indirect game paths or measure the private framebuffer. See [the executable identity, addresses, evidence and limitations](MonsterStrikeWindowSizing.md).

3.8.25 remains the device-confirmed baseline for the affected ad fix, but the orientation-history issue was already reported there. The practical user-confirmed flow is to close the four accounts, restore in portrait, then rotate to landscape; that initializes the preferred game layout without providing dynamic recalculation. A blanket rollback of later host consistency, diagnostics and WebKit timing fixes would not solve the retained game canvas. This investigation changes documentation only and introduces no game patch, forced startup orientation, automatic relaunch or new IPA.

For the affected game, long-press its Dock account (or open its window title menu), choose **Diagnostics → Copy Window Size Diagnostics**, then paste the report into this conversation. Copy once after restore, then again after rotation while showing the same game screen. The report records host content/hosting/remote-scene dimensions, the initial and expected logical sizes, controller submission support/count, and the guest's actual scene/window/root-view and Metal/OpenGL layer bounds. Metal drawable size is included without requesting a drawable or changing the renderer. A bound game stays selected when an ad becomes key. The report also includes both host request/reply snapshots to detect a rotation while collecting it. It collects dimensions/class names only, without screenshots, text, URLs, paths or account data. Reading it does not resize views or invoke layout. Work is bounded and runs only when requested, with one in-flight guest request and a three-second response limit; a timed-out guest remains gated until reply/disconnection. No polling or performance sampling is required.

Changed guest window/screen dimensions with an unchanged renderer layer point to a renderer layout issue. Unchanged guest dimensions instead require checking scene delivery or the game's window handling. If all measured sizes update and proportions remain wrong, the game may cache camera/projection/layout state that is not visible in these dimensions. Reports can distinguish those cases; matching dimensions do not prove the game recalculated.

The screen coordinate-space objects and their point/rectangle converters stay unchanged. UIKit's own geometry queries retain physical dimensions, selected from the immediate caller's system-library image; unidentified callers also retain original behavior. UIKit relies on those original identities and physical transforms when creating or rotating windows. The dimensions option is intended for screen-based sizing; use the window's coordinate space for actual guest input. It does not create a replacement screen or a custom scene transform.

Main-thread queries refresh geometry. Window frame/bounds changes and existing lifecycle notifications refresh a locked snapshot for background SDK reads; background queries do not enumerate UIKit windows or wait on the main thread. No timer or idle polling is added. The last valid dimensions survive temporary scene disconnection. An established game scene remains selected when a popup creates other windows, while ambiguous initial application scenes retain the startup snapshot.

This is a dimensions compatibility option, not a replacement for UIKit scene geometry. It does not change `UIWindowScene.interfaceOrientation`, `UIDevice.orientation`, the physical display configuration, orientation masks, host rendering or Input Sync's window coordinates. An SDK that infers layout from local screen dimensions may improve; one that reads device/scene orientation, cached dimensions or a system view service can still behave differently. WebKit screen dimensions use the compatibility script, but physical/device orientation is preserved. A video designed only for landscape may still require letterboxing or a separate SDK-specific fix.

The UIKit checks exercise the production hooks with a real window, modal close-button hit testing, web viewport layout, retained coordinate conversion, resize, startup and background reads, plus controlled landscape/portrait scene geometry, ad-window replacement and exclusions. They do not load Monster Strike, its advertising SDK or the private remote hosting implementation. The user's 3.8.25 ad result covers their reported ad display; the outstanding orientation-history and broader checks are recorded in [the device checklist](../Tests/MultitaskManualChecks.md).
